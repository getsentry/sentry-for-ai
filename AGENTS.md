# Agent Instructions

## Project Overview
Sentry plugin for AI coding assistants (Claude Code, Cursor, Codex, and Grok). Provides MCP server integration and skills.

## Commit Attribution
AI commits MUST include:
```
Co-Authored-By: (the agent model's name and attribution byline)
```

## Repository Structure

All buildable source lives under `src/` — this repo is not itself an installable
plugin.

```
src/skills/             # Skill library (source of truth)
src/references/         # Shared reference content hydrated into skills at build time
src/plugins/<agent>/    # Per-agent build scripts + manifests
src/SKILL_TREE.md       # Generated skill index (see Skill Tree Navigation below)
```

Per-agent plugin metadata is generated by the `src/plugins/<agent>/build.sh`
scripts and published to each agent's distribution repository; it is not
committed here.

## Skills

`src/skills/` is the shipped set. Superseded per-SDK "wizard" skills are frozen
under `skills-legacy/` and built by nothing — don't edit them expecting a change
to ship, and don't cite them from a shipped skill.

### Standalone Skills
Flat and self-contained — the shape new skills should take. No category, parent,
breadcrumb, or `disable-model-invocation`; the description is the routing signal.

| Skill | Description |
|-------|-------------|
| `sentry-get-started` | Guided entry point — orients to the current setup, runs first-error setup for a new project, routes everything else |
| `sentry-instrument` | Wire up any signal on any platform: errors, tracing, logging, metrics, profiling, session replay, user feedback, crons, AI/LLM monitoring |
| `sentry-debug-issue` | Take one Sentry issue from report to shipped fix, optionally via Seer |
| `sentry-sdk-upgrade` | Upgrade the Sentry JavaScript SDK across major versions |

### Feature Setup
Behind the `sentry-feature-setup` router.

| Skill | Description |
|-------|-------------|
| `sentry-otel-exporter-setup` | Setup OTel Collector with Sentry Exporter |
| `sentry-create-alert` | Create Sentry alerts using the workflow engine API |
| `sentry-snapshots-cocoa` | Setup Sentry Snapshots for Apple/Cocoa projects, including SnapshotPreviews and Apple snapshot CI |

Platform setup code and per-signal strategy are **references**, not skills —
`src/references/sdks/<platform>/` and `src/references/concepts/`, hydrated into
the skills that declare them in a `references.yml`. Adding support for a platform
or a signal usually means editing a reference, not adding a skill.

## MCP Server
Sentry MCP server configured at `https://mcp.sentry.dev/mcp`. The source of truth is `mcp.json`: Cursor consumes it as-is at the plugin root, while the Codex and Grok builds emit it as `.mcp.json` (Codex's validator requires the dotted name; Grok auto-discovers it). Claude declares the server inline in its `plugin.json` (`mcpServers`), so the Claude build ships no MCP file. The root `.mcp.json` is a backwards-compat copy (identical to `mcp.json`) retained for existing installs that consumed the plugin from this repo's root; keep the two in sync until the root compat surface is removed.

## Key Conventions
- All setup skills must **detect platform/SDK before suggesting configuration** — never assume
- GitHub CLI (`gh`) required for PR-related skills
- Avoid emojis in skill/command content — keep output platform-neutral
- A skill's frontmatter `description` is the single place triggers live. Don't
  restate them in the body as an "Invoke This Skill When" section: the body is
  read only after the skill has already fired.
- End a skill on a **checkable** completion criterion, and where telemetry is
  involved make it telemetry actually seen in Sentry via the MCP — not "check
  your dashboard".
- Prompt the target behaviour rather than the banned one. A "DO NOT say X" list
  makes X more available, not less.

## Skill Tree Navigation

**How it works:**
- Skills are either **standalone** (model-invoked, description is the routing
  signal) or **router-backed** (hidden with `disable-model-invocation: true`,
  reached when a router points at them).
- One router ships today: `sentry-feature-setup`. `src/SKILL_TREE.md` is the flat
  sitemap listing every skill.
- Hiding a skill trades context load for cognitive load. It pays off for a router
  fronting several skills with fuzzy boundaries; it does **not** pay off for a
  router with one child, where the router's own description costs as much as the
  skill it hides. Prefer standalone unless the routing genuinely earns the hop.
- Tools that don't support `disable-model-invocation` simply see all skills.

**Categories:**
- `feature-setup` — specific feature configuration (router: `sentry-feature-setup`)
- `internal` — contributor tools, no router

**Adding a new skill — standalone (default):**
1. Create `src/skills/<skill-name>/SKILL.md` with `name`, `description`, `license`
2. Write the description as the trigger list — one trigger per distinct branch,
   no synonyms restating the same one
3. Declare any shared references in `references.yml`
4. Run `scripts/build-skill-tree.sh` to regenerate `src/SKILL_TREE.md` and validate

**Adding a new skill — behind a router:**
1. Steps 1 and 3 above, plus `category`, `parent`, `disable-model-invocation: true`
2. Add breadcrumb as first body line: `> [All Skills](../../SKILL_TREE.md) > [Category](../router/SKILL.md) > Skill Name`
3. Add the skill to the parent router's routing table and its Feature Skills table
4. Regenerate as above

CI validates on every PR via `.github/workflows/validate-skill-tree.yml`.

**Adding a new category:**
- Create a new router skill with `role: router` in frontmatter, add a
  category branch in `scripts/build-skill-tree.sh` (`SKILLS_*` array,
  `column_header`, and an `emit_category_section` call), set the leaf skills'
  `category`/`parent`, and document the category here.
- A category worth creating has enough skills that the router's own description
  costs less than exposing them directly.

**Validation:**
- `scripts/build-skill-tree.sh` — regenerates `src/SKILL_TREE.md`, validates all frontmatter, breadcrumbs, and router tables
- `scripts/build-skill-tree.sh --check` — CI mode, fails if `src/SKILL_TREE.md` is stale or validation errors exist
